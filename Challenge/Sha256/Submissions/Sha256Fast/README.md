# Sha256Fast

Sha256Fast is a fully proved, 2,622-byte SHA-256 implementation for the
EIP-8200 challenge. It hashes calldata directly, uses a fixed 4,480-byte memory
area, and processes one 64-byte message block at a time. The committed raw EVM
bytecode is proved functionally correct and has a proved symbolic gas bound.

## Results

| property | result |
|---|---:|
| bytecode size | 2,622 bytes |
| Tier-1 19-vector gas total | 1,404,867 |
| reference total | 10,179,119 |
| speedup over reference | 7.25× |
| exact marginal cost per full block | 21,229 gas |
| maximum active memory | 140 words / 4,480 bytes |
| functional proof | `Correct bytecode` |
| gas proof | `CorrectWithSchedule bytecode gasSchedule` |

The exact proved execution cost for an input of `n` bytes is

```text
22,552 + 21,229 × floor(n / 64)
        + (21,198 if n mod 64 ≥ 56, otherwise 0).
```

The machine-readable monotone leaderboard schedule is

```text
1,323 + 21,229 × floor((n + 72) / 64).
```

It equals the exact cost when `n mod 64 < 56` and has 31 gas of headroom when
SHA-256 padding requires two final blocks.

## Implementation

The implementation uses three main optimizations:

- A 32-bit word is doubled into a 64-bit value containing two adjacent copies.
  SHA-256 rotations then reduce to a multiplication followed by shifts.
- Intermediate expressions are masked lazily. Only values that must re-enter
  the next round as exact 32-bit words are truncated.
- Eight compression rounds share fixed stack slots whose logical roles rotate.
  The slot mapping returns to its original arrangement after each group of
  eight rounds, avoiding per-round stack shuffling.

The input is copied a block at a time with `CALLDATACOPY`. Padding and the
64-bit bit-length footer are staged in the same fixed scratch region, so memory
does not grow with calldata length.

`bytecode.hex` is generated by `generators/sha256gen4.py`. The generated Lean
instruction and proof-support modules are emitted by the scripts in
`generators/`; `Bytecode.lean` identifies the assembled `Loop.bytes` value with
the submitted artifact checked by CI.

## Proof structure

The proof executes the submitted raw bytecode under the pinned Osaka EVM
semantics. It does not assume the Python generator is correct.

1. `MemoryCorrect.lean`, `ScheduleCorrect.lean`, and `RoundCorrect.lean` prove
   the memory layout, message schedule, and eight-round compression invariant.
2. `CompressionCorrect.lean` composes all 64 rounds with feed-forward and proves
   one compression call implements `Sha256.compressBlock`.
3. The driver modules prove calldata copying, the full-block loop, branch
   control, and preservation of the hash/constants invariants.
4. The tail modules prove byte-for-byte canonical SHA-256 padding, including
   the two-block boundary at remainders 56 through 63.
5. `EndToEndCorrect.lean` bridges the final state to the challenge specification;
   `Proof.lean` exposes `correct : Correct bytecode`.

Gas is proved on the same execution certificates. Static copy-free paths use
an opcode-cost meter with memory expansion as a telescoping potential. Dynamic
copy paths prove their copy-word charge explicitly. The main exact components
are:

| component | gas |
|---|---:|
| initialization, including 0 → 140-word expansion | 1,155 |
| initial full/tail branch | 10 |
| one compression | 21,167 |
| one full-block driver iteration | 21,229 |
| one-block final tail (after initial branch) | 21,387 |
| two-block final tail (after initial branch) | 42,585 |

Initialization contains 697 gas of static opcode work and 458 gas of proved
memory expansion. One compression consists of schedule setup/generation,
rounds, and feed-forward costs proved separately before composition.

## Reproducing the checks

From the repository root:

```sh
python3 Challenge/Sha256/Submissions/Sha256Fast/generators/check_hex.py
lake build Challenge.Sha256.Submissions.Sha256Fast.Proof
lake build Challenge.Sha256.Submissions.Sha256Fast.Gas
lake env lean Challenge/Sha256/Submissions/Sha256Fast/Proofs/AxCheck.lean
lake exe sha256challenge \
  --hex=Challenge/Sha256/Submissions/Sha256Fast/bytecode.hex
scripts/check-sha256-submissions.sh
scripts/report-sha256-gas.sh
```

The axiom check reports only Lean's standard trusted principles used by the
repository (`propext`, `Classical.choice`, and `Quot.sound`); there are no
submission axioms or `sorry` declarations in the proof closure.
